# DEPLOYMENT.md

## Local development (this session's target)

```bash
# terminal 1: rendezvous
cargo run -p rendezvous -- --config deploy/local/rendezvous.toml

# terminal 2: combined ingress+egress relay
cargo run -p relay-agent -- --config deploy/local/relay-combined.toml

# terminal 3: local test HTTP service (what the client tunnels to)
cargo run -p test-service

# terminal 4: client daemon (local SOCKS-style proxy on 127.0.0.1:1080)
cargo run -p client-daemon -- --config deploy/local/client.toml

# terminal 5: exercise it
cargo run -p cli -- diagnostics
curl --socks5-hostname 127.0.0.1:1080 http://127.0.0.1:8081/
```

`deploy/local/*.toml` and the dev keypairs are generated by
`deploy/local/gen-keys.sh` (ed25519, ephemeral, dev-only — never committed
as "the" trust root; regenerated per checkout). See that script's header
comment for what it does and does not provide.

## Split ingress/egress

`deploy/local/relay-ingress.toml` + `deploy/local/relay-egress.toml`
demonstrate the two-hop topology (`docs/ARCHITECTURE.md`); the ingress
relay forwards the framed stream to the egress relay over a second
`direct-tls` hop rather than dialing the destination itself.

## Hostile network simulation

`tests/hostile_network/` uses Linux network namespaces + `tc netem` +
`iptables` to simulate packet loss, latency, and UDP blocking between the
client namespace and the relay namespace. Requires `CAP_NET_ADMIN` (root or
`sudo -E`) and is skipped automatically (not failed) when that capability
is absent — see the test module's `require_root!()` guard. Run with:

```bash
sudo -E cargo test -p tests --test hostile_network -- --ignored
```

## Explicitly out of scope for this deployment doc

Public production deployment (real domains, real TLS certs from a public
CA, real cloud relay fleet, monitoring/alerting stack, container
orchestration) was not built or deployed — no purchase of services, no
push to public infrastructure, per the operating instructions for this
session. What's documented above is a fully local, reproducible dev/test
environment only.

## Linux kill switch / TUN (Phase 9 — deferred)

Not implemented this session: the `KillSwitchBackend` trait
(`crates/policy::killswitch`) and a mock backend are implemented and unit
tested (policy: "no secure route => block", tested against the mock), but
the real Linux backend (nftables rules + a TUN device via `tun`/`nix`)
needs `CAP_NET_ADMIN` and mutates host routing tables — building and
testing it live in this sandboxed session risked leaving the host network
namespace in a broken state with no safe rollback path available here. A
concrete implementation plan (nftables ruleset, TUN setup order, rollback
procedure) is written in the trait's module doc comment for the next
session to implement against.
