## v1.4.0-rc.1 (pre-release, qualification candidate)

Workspace version `1.4.0`. Supersedes `v1.3.1-rc.8` for new two-way installs. Not a stable release. Not accepted on a
device, on real hosts for the two-way profiles, or from a Russian network.

### What is new
- **Bidirectional two-hop on two servers.** A relay can opt in (`[exit_principals] enabled = true`) to also be the
  exit of another relay's route, so servers A and B each serve both profiles: client -> A -> B and client -> B -> A.
  Dedicated exit-principal credentials (`vpn-admin pair issue-exit` on an opted-in relay) leave directly only after one
  scoped block: private/special ranges, SMTP, the node itself and the declared peer are rejected first, so routes
  cannot loop. All other relay users still reach only the declared exits and are otherwise rejected.
- **`doctor`** verifies that block exactly and compares its principals with the accounts the store authorizes; stale
  or unauthorized exit rules on disk fail. This is file-level verification; `doctor --protocol` covers the running
  process.
- **Runbook**: `docs/BIDIRECTIONAL_RUNBOOK.md` (install, enable, pair, two pinned Hiddify links, friend lifecycle,
  backup/update/restore, exit-to-relay migration). Design and migration plan: `docs/BIDIRECTIONAL.md`.

### Compatibility
- Opt-in only. Without `[exit_principals]` nothing changes; existing exit and relay deployments render as before.
- An older binary ignores the new section and the user flag (fail closed: the principal has no route).
- A node's role is never rewritten: converting an exit to a relay is a reinstall (see the runbook). `restore` refuses
  a different role or node id.
- Install the same release on both servers of a pair.

### Known limits
- TCP only through either relay. Google/YouTube: RU->EU exit unverified; EU->RU not qualified. No Shorts claim.
- No real-host, Hiddify-device or Russian-network acceptance of the two-way profiles yet.
